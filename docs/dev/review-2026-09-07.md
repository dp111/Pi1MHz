## A. Can corrupt memory or brick a board

### A1. `rpi/arm-start.S:284` — the chain-boot cache flush compares against `r3`, which is never loaded **[verified here]**

```asm
    mrc     p15, 1, r0, c0, c0, 1      @ Read CLIDR -> r0
    ...
next_level:
    add     r10, r10, #2
    cmp     r3, r10, lsl #23           @ Compare with LoC
    bgt     loop_level
```

The canonical routine loads `and r3, r0, #0x07000000` (CLIDR.LoC) before the
loop. That instruction is absent, and `r3` is live garbage: `_copyandreboot`
runs `BL _fast_scroll` at line 237 and `_fast_scroll` uses `r3` as a copy
register, so on entry `r3` holds the last word copied out of the incoming
kernel image.

Only the `#if (__ARM_ARCH >= 7)` arm, i.e. **kernel7 / A53**. If `r3` is
negative as a signed value — very common, ARM opcodes like `0xe59f1234` are —
`bgt` fails immediately and only L1 is cleaned, L2 never. If it is large and
positive the loop runs to level 8, writes a reserved level to CSSELR, reads an
UNKNOWN CCSIDR and issues `DCCISW` with garbage set/way/level: architecturally
UNPREDICTABLE. Same code, different outcome depending on one image word — the
shape of "release→debug chain-boots fail 5/5".

Partly shielded today because `mtp_fs.c:773` calls `disable_data_cache()` in C
first, but this asm is still the only flush an older outgoing kernel has.

### A2. `rpi/cache.c:377` — reserved TEX/C/B encoding on the VideoCore RAM mapping **[agent]**

`PageTable[base] = (base << 20) | 0x11C06` decodes as TEX=0b001, C=0, **B=1**,
which the ARM ARM lists as Reserved. The file's own comment three screens up
states the intent as `C=0; B=0`, i.e. `0x11C02` — one bit too many. This range
is the GPU's RAM, and `screen_allocate_buffer()` returns physical addresses
inside it: every framebuffer, YUV plane and H264 output buffer is written
through an architecturally undefined memory type, implementation-defined and
free to differ between ARM1176 and A53.

### A3. `framebuffer/screen_modes.c:870` — unchecked GPU allocation, then a full-screen clear through a NULL `fb` **[verified here]**

```c
uint32_t temp = screen_allocate_buffer(pitch * height, &handle);
fb = (unsigned char *) temp;      /* returns 0 on failure, unchecked */
...
screen->clear(screen, NULL, 0);   /* writes width*height bytes from fb */
```

`default_set_pixel_8bpp` is `fb + (height-y-1)*pitch + x`, so with `fb == NULL`
the clear walks from physical 0 — the exception vectors, `Pi1MHz_STRUCT_VADDR`
at 0x100, the shadow/JIM area and the kernel image. This is the same shape as
the recorded `videoplayer_init` "memset 442 KB to address 0" boot lockup.

Reachable from BASIC in one command: `VDU 23,22,255,255,255,255,0,0,0,0` →
`fb_custom_mode(65535, 65535, 256)`; `vdu23_22` only rejects `< 8` pixels.

Secondary, same site: `static uint32_t handle` keeps its old value when the
allocation fails, so the next mode change releases an already-released handle.
The contract fix belongs in `screen_allocate_buffer` (`rpi/screen.c:450`),
which leaves `*handle` unwritten on an allocate failure but writes it and still
returns 0 on a lock failure.

### A4. ~~`rpi/arm-start.S:212` — the .bss clear rounds its start address down, into `.noinit`~~ — **NOT AN ISSUE (owner, 2026-09-07)**

Raised as: `bic r4,r4,#0xF` rounds `__bss_start__` down, so the clear could zero
up to 15 bytes of `.noinit`'s tail.

Rejected, and the layout confirms it. `.noinit`'s last object is `arm_stack`
(0xf6000, size 0x80000), which ends at 0x176000 — exactly `__bss_start__`. So the
bytes below the boundary are the **top of the ARM stacks**, not persistent state:
nothing there survives a boot by design, and the stacks are set up immediately
afterwards. `arm_stack` is also 16K-aligned and 0x80000 long, so `__bss_start__`
is inherently 16-byte aligned and the `bic` is a no-op regardless of what else
goes into `.noinit`. The point of `.noinit` is to *avoid* the zeroing cost, and
that boundary is fine.

Original text kept below for the record only:

> `rpi.ld` places `.noinit` immediately before `__bss_start__`, so this zeroes up
> to 15 bytes *below* it, and it also stores before testing, so it writes up to
> 15 bytes past `__bss_end__`.

```asm
    ldr     r4,=__bss_start__
    bic     r4,r4,#0xF            // 16 byte align
```

`rpi.ld` places `.noinit` immediately before `__bss_start__`, so this zeroes up
to 15 bytes *below* it — the tail of the section whose whole purpose is
surviving a watchdog reset and a chain-boot. It also stores before testing, so
it writes up to 15 bytes past `__bss_end__`.

Masked today: the current build has `.noinit` at 0x84000 size 0xf2000, putting
`__bss_start__` exactly on 0x176000, already 16-aligned. Nothing enforces that
— one added `char` in a `.noinit` array moves it, and the failure mode is a
silently corrupted crash record rather than anything that announces itself.

### A5. Chain-boot image size vs the live page table — **ALREADY FIXED (owner, 2026-09-07)**; was already known besides

The USB/MTP agent reported `mtp_fs.c:774` as an unguarded brick risk: the copy
lands at 0x8000 with the MMU on, `PageTable` is at 0x90000, so the copy reaches
it once the image passes 0x88000 (557,056 bytes; today's is 494,356).

The arithmetic is right and I confirmed the layout, **but this is already
recorded and already measured**: a 573,440-byte padded image chain-booted fine,
because the copy stays in TLB-resident sections. Treat it as a latent hazard
with a known-good data point, not as a wall, and do not quote a hard size
limit. Listed here only so the next review does not re-find it as new.

## B. Silent data loss

### B1. `wifi/webserver.c:5769` — a failed WebDAV COPY destroys an existing destination **[verified here]**

The destination is opened `FA_CREATE_ALWAYS` (truncates immediately) and
streamed into in place. Five teardown paths close `copy_dst`; only one — the
LUN-revoke path at `:5612` — unlinks it. A read error (`:5626`), a write error
(`:5636`), `conn_close` (`:1819`), `conn_reset_for_next_request` (`:2197`) and
`ws_err` (`:6714`) all leave a truncated file where the original was.

The in-file comment claiming this is safe is only true for an *open* failure:

```c
/* No f_unlink for COPY: FA_CREATE_ALWAYS truncates, and reaching it
   only after the source opened means a failed COPY cannot destroy an
   existing destination. */
```

Both other write paths in the same file (`dav_put_tmppath`, `upload_build_paths`)
use `.part` + rename and carry long comments about exactly this hazard, so COPY
is the outlier rather than the idiom. `copy_dst_existed` is already tracked and
is used only on the success path.

### B1a. `rpi/vcsm.c:102` and `rpi/auds.c:117` — the VideoCore fail-fast latch reached one of three copies **[verified here]**

`rpi/mmal_vc.c` carries the `dead` latch and says why:

```c
/* Once a call has timed out the VC side is not coming back for this
   session: fail every later call immediately rather than spending
   another REPLY_TIMEOUT_US each time stalling the main loop. */
if (!client.inited || client.dead)
    return false;
```

`vcsm.c:102` `sendwait()` and `auds.c:117` `send()` are the same two-loop
queue-then-wait shape with **no `dead` flag** — `dead` appears only in
`mmal_vc.c` (declared :41, tested :209, set :230 and :240). Timeouts:
mmal_vc 500 ms, **vcsm 1 s**, auds 500 ms.

So the recorded "VideoCore death starves the Beeb" failure is only half fixed:
once the VC mailbox dies, every `vcsm_*` call burns a full second and every
`auds_*` call half a second inside the cooperative poll loop, and the Beeb
starves exactly as before — just through the other two services. ~40 lines
duplicated three ways; `vchiq.c` has two more copies of the timed poll-wait at
`:654` and `:705`. All three are main-loop-only, so one shared
`vchiq_sync_call()` with a per-service latch is safe.

### B1b. `wifi/webserver.c:3858` — the browser-form upload is the one write path that neither preserves mtime nor notifies MTP **[agent]**

`dav_put_finish` (`:4808-4903`) and `upload_finish` (`:3858-3917`) are the same
close/re-check/unlink/rename sequence — `upload_finish`'s comment even says "the
same reasoning as the WebDAV PUT finalise". But the DAV copy has two fixes the
form copy lacks: the `f_stat`/`f_utime` mtime carry-over, and
`mtp_fs_notify_object_added/changed`. Every other mutation route in the file
notifies MTP (DELETE `:5460`, MKCOL `:5518`, COPY `:5663`, MOVE `:5738`, `:5824`),
so this is the single hole: a connected MTP host keeps serving the stale object,
and the uploaded file always shows the `FF_FS_NORTC` default date — the exact
symptom the DAV comment at `:4854` describes.

Note also that this file now answers "replace a file safely" three different ways
(`.part`+rename for PUT and form upload, `FA_CREATE_ALWAYS` in place for COPY —
see B1), and a fourth exists at `BeebSCSI/filesystem_safewrite.c:61` (`.new` +
**byte-for-byte readback verification** + `.bak` + rollback) — the only one that
verifies, on a card documented to have silently short-changed writes.

### B2. `rpi/sdcard.c:1651` — the R1 card status returned by READ/WRITE is captured and never examined **[agent]**

`sdhost_issue_raw_command` stores R1 in `dev->last_r0`, which is read for CMD8,
ACMD41, CMD3, CMD7 and CMD13 and **nowhere** in `sd_do_data_command`. Success is
declared purely on controller flags. A CMD24 to a write-protected card or past
its capacity returns a valid, correctly-CRC'd R1 carrying `WP_VIOLATION` /
`OUT_OF_RANGE`, with no `SDCMD_FAIL_FLAG` and no `SDHSTS_ERROR_MASK`: `sd_write`
returns `buf_size`, `disk_write` returns `RES_OK`, FatFs updates its metadata.

Related: the error paths clear `last_cmd_success`/`last_interrupt`/`last_error`
but not `last_r0`, so after a failure it still holds the previous response.

### B3. `uef_service.c:192` — `guard_stamp()` writes page 255 and destroys the length trailer **[verified here]**

```c
#define UEF_TRAILER      (UEF_BASE + 0xfffeu)
#define UEF_GUARD_OFFSET 0x97u
#define UEF_GUARD_LENGTH (256u - UEF_GUARD_OFFSET)   /* 0x69 */
   for (page = UEF_FIRST_PAGE; page < 256u; page++)  /* <-- 256 */
```

Page 255 covers `0xFF97..0xFFFF`, which contains the trailer at `0xFFFE`. Both
window macros reserve the last page (`256 - FIRST_PAGE - 1`), so page 255 exists
*only* for the trailer — the comment claiming "the guard ends exactly at the
page top … which leaves the length trailer intact" has it backwards.

Masked inside `window_lay_out` (which stamps then re-writes the length) but not
at `:507`, the normal order in which the ROM publishes its guard before opening
a tape. The trailer then holds two arbitrary bytes of the ROM's own filing-vector
code, and an `APPEND` with `length == 0` — the documented "read my length from
the trailer" form — appends an arbitrary number of bytes from JIM page 0.

Fix is one character: `page < 255u`.

### B4. `usb/mtp_fs.c:1889-2056` — MTP response codes returned from the DATA phase **[agent]**

Every error exit in `fs_send_object_info`'s `MTP_PHASE_DATA` arm returns a
positive code; `fs_dispatch_op` then transmits `p_container->header->len` bytes,
which in the data phase is the host's ObjectInfo dataset length (~110), not 12.
The driver then unconditionally continues into `tud_mtp_data_complete_cb`, which
rewrites the same buffer the first response may still be transmitting from and
sets `code = MTP_RESP_OK`.

`fs_send_object` documents this exact hazard and defers the code via
`failed_resp`; `fs_send_object_info` and `fs_set_object_prop_value` do not.
Architecturally: no DATA-phase handler may return a response code.

### B5. `usb/mtp_fs.c:2112-2117` — an unknown-size SendObject ending on a short packet wedges **[agent]**

`tud_mtp_data_receive` sets `total_len = UINT32_MAX` and the driver's completion
test does not treat a short packet as end-of-phase, but mtp_fs only re-arms the
endpoint on a *full* packet. Any host sending `ObjectCompressedSize` 0 or
0xFFFFFFFF with a file length not a multiple of 2048 hangs: no response, the
`FIL` left open, the `.part` on the card, and `filesystemHostLockLun` still
asserted against the Beeb's LUN. For `kernel.now` the 4 MB buffer is held too.

## C. Beeb-visible hangs and poll-loop stalls

### C1. `BeebSCSI/scsi.c:1088, 1231, 2533` — a host that stops ACKing costs 100 ms per sector **[agent]**

`hostadapterPerformReadDMA` returns short on `hd_wait_ack()` timeout, but in a
release build `DEBUG_bytesTransferred(x)` is `(void)(x)` — the return is
discarded and the loop starts the next sector. A `READ6` of 256 blocks to a host
that stopped servicing REQ without asserting nRST burns 25.6 s with the whole
cooperative loop stopped. `scsiCommandReassignBlocks:919` already bails out of
its per-byte loop with a comment explaining precisely this composition rule;
READ6/WRITE6 never got the same treatment.

### C2. `BeebSCSI/scsi.c:2064` — SEND DIAGNOSTIC drains a host-supplied 16-bit count with no bail-out **[agent]**

No `hostadapterReadResetFlag()` check and no ACK-timeout bail, so a count of
65535 with no data following is 65535 × 100 ms ≈ 1.8 hours with the poll loop
dead — and unlike C1 a BREAK does not shorten it, because `hd_wait_ack()`
returns immediately on reset while the loop still grinds through every
remaining iteration.

### C3. `fat_service.c:277-377` — file/dir commands never check the handle was opened **[verified here]**

```c
NOINIT_SECTION static FIL fileObject[16];   /* .noinit is NOT zeroed */
...
case 4: result = f_lseek(&fileObject[data & 15], ...);
        result = f_read (&fileObject[data & 15], ...);
```

`data & 15` comes straight from the Beeb's command register, and commands 3/4/5/6
(and 8/9 on `dirObject`) run against the slot unconditionally. FatFs's own gate
dereferences `obj->fs` — uninitialised DRAM on a cold boot — **in FIQ context**.
`fat_open_valid[]` already records "this handle is open" but is used only by the
webserver interlock, never as a gate.

### C4. `fat_service.c:215, 284` — unbounded FatFs/SD work in FIQ **[agent]**

`fat_service_command` is called from a `WRITE_FRED` callback. The per-command
caps are the whole region, not a transfer bound: `sectors` up to 65536 (32 MB)
and `buf_len` up to 16 MB. A single command can hold FIQ for ~2 s at 17 MB/s,
during which no 1 MHz bus cycle is serviced. AUN and net both latch and defer;
FAT calls `f_read`/`disk_read` inline. This is a *duration* finding, not the
previously-rejected FIQ-vs-main-loop concurrency question.

### C5. `M5000_emulator.c:435-472` — `music5000_rec_stop()` does an unbounded `f_open` loop and one multi-hundred-MB `f_write` from a poll callback **[agent]**

Reached from `music5000_emulate()` and from `store_samples()` — the latter inside
the per-sample loop filling the audio DMA block. The recording buffer is bounded
only by `JIM_ram_size*16MB - 32MB`, ~384 MB on a 512 MB Pi. Five minutes of music
is ~56 MB in one `f_write`; a long session blocks for ~40 s against a 15 s
watchdog. A card already holding `Musics000..999.wav` costs 1000 directory scans
in the same callback.

### C6. `framebuffer/primitives.c:1765, 1920` — two unclipped O(w·h) loops in IRQ context **[agent]**

`prim_move_copy_rectangle` clips *inside* the loop body, so the iteration count is
set entirely by the Beeb's coordinates — up to 32768×32768 ≈ 1.07e9 iterations in
`IRQHandler_main`, with the watchdog unkicked.
`MODE 21 : VDU 25,4,0;0; : VDU 25,4,32000;32000; : VDU 25,189,0;0;` is enough.

`prim_define_sprite` has the same shape plus a size overflow: at 32bpp,
`width = height = 32768` gives `(32768*32768) << 2` = 2^32, so `size` wraps to 0,
`malloc(0)` returns a valid block, the NULL check passes, and the loop writes 2^30
words through it.

### C7. `framebuffer/fonts.c:246` (and `screen_modes.c:905, 989`, `framebuffer.c:419`) — the text layer writes pixels with no clipping **[verified here]**

`default_write_char`'s scale loop calls `screen->set_pixel` with no bounds test,
and `default_set_pixel_8bpp` does no clipping of its own — the primitives layer
clips every write (`primitives.c:160`), the text/font layer does not.
`VDU 23,19,1,<h>,<v>` accepts any scale 1..254 and nothing clamps it against the
screen. In MODE 21, `VDU 23,19,1,1,100` gives `font_height = 800`; printing any
character then walks to `y - 799 = -288`, up to 184 KB past the end of a
327,680-byte framebuffer. `VDU 12` and `invert_cursor` spill the same way.

## D. Video correctness (all confirmed, all cheap to fix)

### D1. `rpi/screen.c:910-913` and `:1431-1432` — the YUV plane and the dim strips omit the uncached bit on their polyphase-kernel pointers **[verified here, two agents]**

`setup_polyphase()`'s own comment states the rule: *"These are live only because
the kernel pointers carry the uncached bit … without it this table was written
correctly and never read, and the plane filtered with whatever the GPU firmware
had loaded."* Both `screen_create_RGB_plane` paths write
`POLYPHASE_BASE | 0x80000000u`. `screen_create_YUV420_plane` writes bare
`POLYPHASE_BASE` on all four pointers, and `dim_strip_place` on both of its two.

So the plane doing the largest resample — 768→1664 H, 576→1152 V — is filtered by
whatever kernel the VideoCore firmware last loaded, not the Mitchell table written
twenty lines earlier. The sharper-kernel work at HVS 0xf40 has no effect on video
at all, and the computer plane and the video plane filter with two different
kernels, which undercuts the whole "register both planes to one grid" design.

### D2. `rpi/screen.c:660, 667` — the YUV scale path has no horizontal clamp, so `h_overscan` underflows **[verified here, two agents]**

The RGB path clamps both axes; the YUV path handles height by cropping and does
nothing for width, and `h_display - *scaled_width` is `uint32_t`. With
`VIDEO_GRID_WIDTH` 832 and the `yuv_scale` switch:

| display | yuv_scale | scaled_width | startpos x |
|---|---|---|---|
| 640x480 | 0.875 | 728 | **4052** |
| 800x600 | 1.125 | 936 | **4028** |
| 1024x768 | 1.5 | 1248 | **3984** |
| 1280x1024 | 2.0 | 1664 | **3904** |
| 1280x720 | 1.375 | 1144 | 68 (ok) |
| 1920x1080 | 2.0 | 1664 | 128 (ok) |

On any 4:3 HDMI mode the Domesday video plane is parked off-screen while
`videoplayer_active()` and the `/status` player row both report healthy. Only the
16:9 modes escape, which is why it is latent on this bench. The file's own TODO
at line 597 already says it "will work really badly with an 800x600 screen mode".

### D3. `rpi/screen.c:803` — `vc4_ppf()` mis-ports upstream's 16.16 `offset2` **[agent, two agents]**

Upstream receives `src` already in 16.16 and computes `scale = src / dst`, so
`offset2 = src - dst*scale` is the division remainder, a sub-LSB correction. This
port fixed the scale line (`(src<<16)/dst`) but left `offset2` using the raw
integer `src`, giving `offset2 ≈ -src*65535`; after `>>10` and `>>1` the surviving
low 7 bits are `-(src & 3) * 32`.

Exactly zero when `src % 4 == 0`, which is why it has never shown. Every mode
width is a multiple of 4 — the exception is `.height = 250`, used by five modes,
which get `vpf0` phase `+32` instead of `-32`: the half-pixel pre-roll becomes a
half-pixel *forward* shift, one source line of vertical displacement. Directly
relevant to the open "top row" / "pointer one pixel high" work.

Secondary: `xy` is passed as an integer pixel position where upstream passes
16.16, so `offset = (xy & 0xffff) >> 10` reads bits 10-11 of a pixel count.

### D4. `rpi/screen.c:764, 773-779` — `vc4_ppf`'s `channel` argument is 0 at all ten call sites **[agent, two agents]**

The chroma quarter-pixel branch is dead, and the two calls *labelled* chroma pass
0 anyway. The doubled-destination trick gets the scale factor right but the phase
is the luma half-pixel offset instead of the chroma quarter-pixel one — a
half-chroma-sample colour/luma registration error on the video plane, worst on
high-contrast edges.

### D5. `rpi/screen.c:589, 671` — `screen_scale()` returns a stale crop offset on the no-crop path **[verified here]**

`static uint32_t offset` at function scope; the no-crop path returns whatever a
previous call left in it, where the RGB path correctly returns a literal 0. A
stale non-zero value crops and vertically shifts a picture that needs no crop.
Reachable on an HDMI mode change, because `yuv_scale` is latched forever on first
use while `v_display` is re-read every call. Same class: `rgb_scale`, `fb_scale`,
`fb_scale_x/y`, `xoffset`, `yoffset` are all file statics with no reset path, so
every derived geometry keeps the first display's numbers after a hotplug.

### D6. `rpi/screen.c:1537-1543` — `screen_geometry_report()` reads the live display list **[agent, two agents]**

Eighty lines above, `screen_dim_strips` states the rule and the evidence:
*"The computer plane's rectangle from the SHADOW, never from the live display
list … (pos has been read back as 2061,1 on a 1920-wide display)."* The read
cannot corrupt anything, but `/status` sampled mid-composite reports x=2061 y=1
while `screen_dim_strips_report()` next to it uses the shadow and reports the
truth — two adjacent rows disagreeing. `pos`/`scale`/`src_size` are all already in
`plane_shadow[]`.

### D7. `videoplayer.c:649` — `pvf_reopen()` drops a decoded frame buffer without recycling it **[agent]**

`vp.pending_phys = 0` without handing the buffer back; the slot keeps
`with_caller = true` in h264dec so it is never re-armed. Every other path that
abandons a pending frame recycles it first, one of them with a comment explaining
why. `NUM_FRAME_BUFFERS` is 2, so one jukebox/remount during playback leaves the
decoder single-buffered; a second leaves it with none and the picture freezes
until a BREAK.

## E. Protocol and state-machine defects

### E0. `wifi/wifi_lwip.c:1480` → `wifi/wifi.c:672` — the ERROR retry destroys Beeb-supplied credentials and can latch the stack permanently DISABLED **[verified here]**

The 60 s ERROR-backoff retry calls `wifi_init()`, whose first act is
`wifi_config_load(&g_wifi_config)` → `memset(config, 0, sizeof *config)` followed
by a re-read of `wifi_ssid` from Pi1MHz.cfg. Everything `wifi_service.c` put there
via `wifi_reconfigure_and_rejoin()` — ssid, password, security, `enabled = true` —
is destroyed.

Failure scenario, and it is the *documented* ElkWiFi setup: Pi1MHz.cfg has no
`wifi_ssid` because the Beeb supplies the network. The user types
`*JOIN MyNet mypass` and the Pi joins. Later a transient fault latches
`WIFI_STATE_ERROR` — `wifi_lwip.c:1015` "chip MAC unavailable" is enough. 60 s
later the retry zeroes the config, `have_ssid` is false, so `enabled = false`, so
`wifi_validate_config()` takes the `!enabled` branch and sets
`WIFI_STATE_DISABLED`. From there `wifi_boot()` early-returns, and the ERROR
ladder is gated on `state == ERROR` so it can never fire again. `WiFi.profile` is
only re-read on a BBC reset. **An absorbing dead state produced by the recovery
path itself.**

Two masters for one resource: `wifi.c` treats Pi1MHz.cfg as authoritative on every
`wifi_init()`, `wifi_service.c` treats `WiFi.profile` as authoritative. The
ordering that saves the normal path (`"wifi"` polls before `"WiFiSvc"`) does not
apply, because this call is out of band. The retry should re-run bring-up from the
*live* config rather than re-parsing.

### E1. `wifi/sdio.c:5939` — the optional SDIO probe power-cycles the CYW43 and destroys the working link **[agent]**

`WIFI_BOOT_STAGE_OPTIONAL_PROBE` runs *after* the runtime has reached
`STAGE_DONE`, and `sdio_host_open_start()` unconditionally drops WL_REG_ON,
wiping the chip's firmware, NVRAM and CLM. The probe re-identifies the card,
enables fn1 only, never re-downloads firmware, and leaves the bus at 400 kHz
1-bit while the runtime still believes it is 4-bit/50 MHz. Gated behind
`wifi_sdio_probe` (default off) — a diagnostic that is guaranteed to break what
it is diagnosing. It also blocks the poll loop for several seconds with no yield.

### E2. `wifi/sdio.c:6946-6978` — `powersave_verify_poll()` retries WLC_GET_PM forever **[agent]**

`g_runtime_pm_query_wanted` is cleared only on link-down. Every other one-shot
poller (rssi, pktcnts, rate) clears its `_query_wanted` when the deadline expires;
this one re-arms instead. A firmware that does not answer `WLC_GET_PM` gets a
fresh control frame every 250 ms for the life of the association — an ioctl pair
and a consumed SDPCM sequence number each time. One-line fix.

### E3. `wifi/sdio.c:4279-4368` — the control-frame TX path never wakes the bus **[agent]**

The three data-frame senders all call `sdio_runtime_wake_bus()` first; the only
control-frame sender does not. The data path's own comment spells out the cost:
*"an idle link's first transmit could land on a sleeping interface, which swallows
the frame while the host sees success: sequence consumed, one credit leaked."*
Every control send inherits the gap — rssi, pktcnts, rate, powersave, scan,
disconnect, radio enable/disable, and every join/txglom/mac step. Mitigated only
by the accident of the 10 ms RX sweep calling `wake_bus`, which is skipped while
the DAT1 gate reads asserted.

### E4. `wifi/sdio.c:4822-4824` — function statics in `ack_interrupts_step()` survive a runtime restart **[agent]**

`started`, `round_count`, `no_hmb`, `poll_deadline_us` are the only per-stage
state kept out of reach of `sdio_runtime_start()` and
`sdio_runtime_boot_reset_state()`. A restart from `STAGE_ACK_INTERRUPTS` skips the
initial INT_STATUS ack entirely and returns "done" on the first call, so the
DEVREADY/FWREADY handshake never completes and the restart succeeds into a deaf
chip.

### E4a. `wifi/wifi_lwip.c:1555-1564` — the RX drain shreds a millisecond of inbound frames when the pbuf pool is exhausted **[agent]**

`wifi_lwip_deliver_rx_frame()` returns false only on `pbuf_alloc` failure, and the
frame is then *lost*. The inner drain honours that and breaks — but it has already
set `drained_any = true`, and the outer loop breaks only on `!drained`. So on pool
exhaustion the outer loop immediately re-enters, pulls the *next* frame out of the
chip FIFO, fails to allocate again, and discards that one too, until the 1200 µs
budget expires. Nothing in the loop frees pbufs. A sustained upload therefore
shreds up to a millisecond's worth of inbound TCP segments instead of leaving them
in the chip FIFO for the next pass — the opposite of the stated intent. The drain
needs to report *why* it stopped.

### E4b. `wifi/wifi_lwip.c:831-859` — the reserved TX slots are not reserved **[agent]**

The glom feed treats bulk IPv4 TCP *and UDP* as capped, but the fall-through
re-offers a refused frame with `is_tcp = wifi_lwip_frame_self_retries(...)`, which
is true only for protocol 6. So a UDP frame refused by
`WIFI_LWIP_TX_QUEUE_TCP_MAX` is accepted into one of the four reserved slots on
the second push. With `wifi_txglom>=2` and a UDP bulk source, the queue reaches
32/32 bulk and the next ARP reply or ICMP echo is dropped — exactly the ping loss
the reservation was written to fix.

### E5. `net_service.c:539-554` — `net_dns_found` has no generation or name guard **[agent]**

lwIP's `dns_gethostbyname` cannot be cancelled, and `do_close()` just memsets the
handle. Open a slow URL, close it, open a different URL on the same handle: the
first query completes into the new handle and the connection is made to the *old*
address while `Host:` and the request path name the new one. The same file already
solves this properly for the utility paths (`netutil_ping_generation`), with a
comment saying exactly why.

### E6. `net_service.c:2173-2177` — BBC reset re-init resets `rx_size` but not the ring pointers **[agent]**

`net_service_init()` sets `rx_size` back to 8192 and `net_rx_big_owner` to -1 while
`rx_head`/`rx_tail`/`rx_count` can still be up to 65535 from the borrowed 64 KB
ring; the actual teardown is deferred to the poll, and `"wifi"` polls before
`"net"`. `ring_free()` then underflows (`8192 - 40000` wraps), the fit test passes,
and `ring_put_pbuf` writes ~32 KB past its row. Fix either way: don't touch
`rx_size` in init, or zero the three pointers in the same loop.

### E7. `net_service.c:496-521` — an accepted connection's handle is unreachable if the listener closes **[agent]**

The accepted handle's index lives only in the listener's one-deep `accept_h`.
`do_close()` on the listener never touches it, so it stays `NET_ST_CONNECTED` with
a live pcb: permanently busy, peer never closed. Seven times and the service is out
of handles until a BBC reset.

### E8. `services_emulator.c:136, 144` — the auto-increment wrap tests 32 MB while the address registers cover 24 bits **[verified here, latent]**

`DISC_RAM_SIZE` is 32 MB but the three FRED registers address bits 0-23 only.
Incrementing from `BASE+0xFFFFFF` gives `BASE+0x1000000`, still below
`disc_ram_max`, so no wrap occurs and **bit 24 stays set for the rest of the
session** — every later address-register write ORs into a base 16 MB too high,
and the `+0/+1/+2` readback only publishes bits 0-23 so the Beeb cannot see it.
Only a BBC reset recovers. Reaching 0xFFFFFF is unlikely in current ROMs.

### E9. `BeebSCSI/harddisc_emulator.c:233-258` — `hd_juke_service()` defeats `scsiJukebox()`'s only safety check **[agent]**

`filesystemReset()` → `filesystemDismount()` clears every LUN's status *before*
`scsiJukebox()` runs its "refuse if any LUN is mounted" loop, so the guard is
structurally unreachable on this path and its `bool` return is dropped. A
`*SCSIJUKE 2` poke can switch directory underneath a mounted ADFS; the BSSELECT
path does honour the refusal, so the same operation behaves differently depending
on which door it comes through. Either check before the reset, or delete the
vestigial guard — it cannot stay where it is and mean anything.

### E10. `BeebSCSI/filesystem.c:607-625` — `filesystemReadLunUserCode` reads 5 bytes from a `strlen+1` allocation **[agent]**

`LDUserCode` is a `STRING` key and `store_string()` allocates `copylen + 1`, not
`key->max` — only `NUMSTRING` allocates `max`. `LDUserCode=12` gives a 3-byte
allocation and bytes [2..4] come off the end of the heap block, then go to the
Domesday AIV software as the disc's user code. The comment on the key table shows
this was found once and "fixed" by bumping `max` 4→5, which only covers values
that are exactly 5 characters. The check needs to be on `.length`.

## F. Layering

### F1. `BeebSCSI/scsi.c:1156, 745, 1509` — VFS writes are refused with CHECK CONDITION and skip their data-out phase

The code is deliberate and carries its rationale:

```c
/* VFS write-protect: LUN >= 8 is read-only LaserDisc media and the VFS
   ROM never issues WRITE6 ... Refuse at command phase - a tripwire for
   any unexpected writer. */
```

but it contradicts the rule in CLAUDE.md — *"Beeb writes are silently
accepted-and-discarded — never refused with an error, because the Beeb's FS
handshake loops have no timeouts"* — and the filesystem layer contradicts itself
on the same point: `filesystem.c:943-947` states the rule, `filesystemWriteNextSector`
obeys it, while `filesystemWriteAttributes:1203`, `filesystemFormatLun:1240` and
`filesystemOpenLunForWrite:1644` all return false for LUN ≥ 8.

Because the refusal is placed *before* `ITPHASE_DATAOUT`, a writer that does reach
it is left waiting on REQ mid-transfer rather than getting a clean error.

**This is a decision, not a defect — it needs the owner's call**: keep the
tripwire (and accept the rule's exception, ideally written down), or run the data
phase, discard the bytes and return GOOD.

### F2. `BeebSCSI/filesystem.c:763-847` — `filesystemCheckLunImage()` is a query that starts the LUN **[agent]**

It sets `fsLunStatus[lunNumber] = true` inside a function named "Check", and
`scsiCommandModeSelect6` calls it purely as a predicate. A bare MODE SELECT with
no MOUNT leaves the LUN marked started with its `.dat` held open: BSSELECT then
refuses to jukebox and MTP/WebDAV refuse to write the image, until something
issues an explicit STOP that ADFS never sends. The transition belongs in
`filesystemSetLunStatus`, its one owner.

### F3. `BeebSCSI/filesystem.c:787` — VFS LUNs are opened `FA_READ | FA_WRITE` **[agent]**

Taken for LUN ≥ 8 as well as < 8, and FatFs returns `FR_DENIED` for a write-mode
open of an `AM_RDO` file. Marking `/BeebVFS1/scsi0.dat` read-only — the natural
thing to do to read-only media, and something an MTP copy can carry across — then
stops the LUN starting at all. LUN ≥ 8 should open `FA_READ`.

### F4. `framebuffer/primitives.c:1263-1285` — the rasteriser writes the VDU layer's cursor variables **[agent]**

`prim_fill_area` reaches out to `framebuffer.c`'s `g_x_pos`/`g_y_pos_last1`,
extern'd with the apologetic comment "occasionally manipulated by primitives". The
OS's post-fill cursor rules are VDU-layer semantics keyed to the PLOT code, and
`vdu_25` already owns that dispatch. Returning the span would keep the pixel layer
pixel-only and remove the only `framebuffer.h` include from `primitives.c`.

### F5. `BeebSCSI/scsi.c:1786-1793` vs `fcode.c:264-287` — the AIV disc-flip is implemented twice **[agent]**

Both compute the partner side identically, but only the F-code copy sets
`fc_tray_open`/`fc_tray_open_us`. A host that ejects with `STARTSTOP` gets the disc
swapped without the player ever reporting `O`, so its post-eject poll sees "loaded"
against a volume still being remounted — the same class of bug as the recorded
"Ejecting …" hang. The disc-flip is player state; SCSI should call one helper in
fcode.c.

### F6. `wifi/sdio.c:6154-6173` — `STAGE_WAKE_KSO` does three other stages' work **[agent]**

Clock raise to 25 MHz, 4-bit width negotiation and 50 MHz high-speed negotiation
are hung off the tail of the KSO success branch rather than each having its own
`SDIO_RUNTIME_STAGE_*` case, which is the idiom of every other line in the
function. These are also the only blocking calls left in the stage machine: healthy
hardware costs ~10 ms in one tick, a controller that stops answering costs each
its full 100 ms `TIMEOUT_WAIT` plus up to ~30 commands at 100 ms each.

  `asm-helpers.h`, so on the rpi3 build they get the clobber-less versions —
  including `mtp_fs.c:769`'s `_disable_interrupts()` immediately before
  `disable_data_cache()` and `_copyandreboot()`. Two definitions of one primitive
  with different correctness properties, chosen by which header a TU happens to
  include.
- `rpi/cache.c:145-152` — no `DSB` between `CleanDataCache()` and the `SCTLR.C`
  clear in `disable_data_cache()` on the ARMv7/8 path, and `CleanDataCache()` has
  no trailing DSB of its own. Set/way maintenance is not architecturally complete
  until a DSB, and `InvalidateDataCache()` afterwards discards rather than cleans.
  This is the `kernel.now` path; kernel7/A53 needs a hardware boot test regardless.
- `rpi/cache.c:439` — the ARMv7/8 TTBR0 declares the walk Shareable while every
  section descriptor above has S=0. The ARMv6 path's comment explicitly avoids
  exactly this mismatch.
- `rpi/sdcard.c:1545` — CMD12 recovery calls `sdhost_reset_controller()`, which
  **assigns** `hcfg` and so destroys `SDHCFG_WIDE_EXT_BUS`, and resets `cdiv` to
  the identification divider. Nothing re-runs the clock switch or ACMD6, so the
  card stays 4-bit while the host samples DAT0 only.
- `rpi/sdcard.c:1312, 1488` — a partially-failed init leaves `card_rca` non-zero,
  and the only re-init gate is `card_rca == 0`, so `disk_status` reports OK on a
  card that never finished initialising and nothing ever retries.
- `rpi/sdcard.c:1050-1096` — three independent `timeout` budgets in one
  `sd_issue_command` (15 s total at the 5 s the caller passes), against a 15 s
  watchdog that is only kicked around the mount, never inside the driver.
- `rpi/sdcard.c:940-941` — the PIO stall deadline is declared *inside* the outer
  loop, so the 1 s budget restarts on every 16-word burst; a dribbling card can
  hold a 16-sector read for ~128 s.
- `wifi/webserver.c:936-943` — over-long request URIs are silently truncated and
  still reported as success, which makes the `414`/"path too long" guards at
  `route_files_get:3709` and `dav_url_to_sdpath:4185` unreachable for the request
  target. A 560-character PUT overwrites a *different* file.
- `wifi/webserver.c:5113, 6283, 6357` — `Transfer-Encoding` and `Content-Length`
  are read into 32/24-byte buffers that `ws_find_header` silently truncates, and
  unlike `start_download:3471` these framing decisions carry no
  `strlen(hdr)+2 <= sizeof hdr` guard. `TE: identity;q=<22 chars>, chunked`
  truncates away the "chunked" and the body is parsed as a pipelined request.
- `wifi/webserver.c:6289-6299` — the keep-alive drain's Content-Length parse has no
  overflow guard where the other two parsers in the same file do; `4294967296`
  wraps to 0 and the body is parsed as the next request line.
- `wifi/webserver.c:4590-4634` — PROPFIND walks a whole directory and builds the
  entire multistatus synchronously in the lwIP RX callback, with **no entry cap**
  (the HTML path has `WS_LISTING_HARD_CAP 8000`), then copies the whole body into a
  second buffer while the first is live. COPY was explicitly made one chunk per
  poll tick for exactly this reason; the two directory walks never got the same
  treatment.
- `wifi/webserver.c:3332, 4590` — an `f_readdir` error is indistinguishable from
  end-of-directory, so a card error mid-walk produces a 207 listing the client
  takes as authoritative. The OOM case immediately below is handled correctly, with
  a comment naming this exact hazard.
- `wifi/webserver.c:1979` — `/bench.bin` transmits whatever is in `dl_buf`, which
  is zeroed only once at accept; on a kept-alive connection after a file GET it is
  the last 32 KB of that file, repeated.
- `wifi/webserver.c:4768, 4756` — `dav_put_flush` discards `ws_error`'s return,
  which on OOM has already `tcp_abort`ed and `free`d the connection; the
  propagation then keeps touching `c`. `ws_copy_step`'s three sites return
  immediately and are safe, so these two are the outliers.
- `wifi/webserver.c:2933-2943` — the `/status` "Poll max us" row stops around the
  11th of fifteen pollers with no ellipsis, and because it exits before calling
  `Pi1MHz_poll_max_us(i, true)` the late-registered pollers (including `wifi` and
  `audio`) are never read *or* reset and can never appear. `tmp` is also not
  pre-cleared, unlike the sibling block.
- `wifi/webserver.c:383` — `ws_sd_free_want()` reads as a predicate but arms a
  background FAT sweep, and fires once per directory in a Depth:1 walk. The
  `sdio_runtime_request_rssi()` / `..._get_rssi()` pair ten lines away is the
  idiom.
- `wifi/sdio_host.c:872-886` — `sdio_host_last_error()` calls
  `sdio_host_refresh_status()`, which overwrites the error string with an
  "override is ignored" notice, so setting `wifi_sdio_host` in the cfg loses the
  genuine failure cause from `/status`. `sdio_host_backend_name()` has no callers.
- `wifi/sdio.h:244` vs `sdio.c:538` — two independent definitions of the same
  164-byte limit; the overflow guards test one, the wire buffer is sized by the
  other. Equal today by coincidence; the header comment invites raising one of
  them. Needs a `_Static_assert`.
- `BeebSCSI/scsi.c:1855, 1935, 1989` — VERIFY, READ CAPACITY and READ DEFECT
  DATA(10) return CHECK CONDITION without setting a sense code, so the host's
  mandatory REQUEST SENSE is told "no error". Every other failure path in the file
  sets one.
- `BeebSCSI/scsi.c:871-880` — REASSIGN BLOCKS reads both LongList and LongLBA from
  bit 0; the comment names bit 1. A host sending `data[1] = 0x02` has its 8-byte
  LBAs read four bytes at a time and the protocol desyncs.
- `BeebSCSI/cpuspecific.h:9-10` — `cli()`/`sei()` are empty macros (they must be:
  the ACK arrives via FIQ). Every `cli(); …DMA…; sei();` pair in scsi.c is
  vestigial, `scsi.c:2526` calls a bare `sei()` with no matching `cli()`, and the
  comments at `:2110`/`:2170` describe an AVR that no longer exists.
- `fcode.c:86-108` — the deferred-acknowledgement slot has no queue, so a `?P` poll
  arriving before the host reads the reply overwrites a completed `A2` permanently
  (`videoplayer_take_stop_reached()` is one-shot).
- `teletext_emulator.c:394-403` — the poll loop mutates FIQ-owned
  `ttx_row_ptr`/`ttx_col_ptr`/`ttx_row[][]` without masking, where the two
  `ttx_status` RMWs twenty lines away are explicitly guarded with comments.
- `ram_emulator.c:132-158` — the RAM emulators register their FIQ bus callbacks
  *before* checking that JIM RAM exists, so the "disabling RAM page emulator" log
  is a lie and the callbacks stay live; `rambyte_emulator_init` has no RAM check at
  all. `Pi1MHz->JIM_ram` is also used unguarded by `helpers.c:146` and
  `M5000_emulator.c:568`.
- `Pi1MHz.c:327` — `Pi1MHz_Register_Memory()` does no bounds check and
  `config_emulator_override` accepts any non-negative address, so a FRED
  registration with `addr > 255` silently lands in the JIM quadrant
  (`BeebSID_addr=0xF0` is enough).
- `Pi1MHz.c:462-465` — the nRST interrupt calls `hd_emulator_bus_reset()` with no
  test of `emulator[Harddisc].enable`; with `Harddisc_addr=-1` it writes SCSI
  status to &FC00/&FC01 and clears the Helpers slot's nIRQ mask on every BREAK.
- `M5000_emulator.c:478-487` — the WAV recording path applies gain with no
  saturation and overflows both `int16_t` and `int32_t`; the live path deliberately
  widens to `int64_t` for exactly this reason. `M5000_Gain=16`, the value the
  header comment gives as an example, inverts every loud passage.
- `framebuffer/fonts.h:34-44` — font metrics are plain `char`, unsigned on ARM and
  signed on the x86 conformance host, so `VDU 23,19,1,200,200` behaves differently
  under `tools/vdutest` than on the target. The harness is this code's oracle; a
  divergence that exists on only one of the two builds is what it cannot see.
  `int8_t`/`uint8_t` pins it.
- `framebuffer/primitives.c:446-451, 582-587` — ellipse coefficients overflow `int`
  at about 1300×1300 pixels (`a2 * y` is `width²·height`), long before the
  coordinates run out; `sigma` overflows earlier. Unrelated to the known ellipse
  *shape* difference — this is the arithmetic.
- `framebuffer/framebuffer.c:1500-1533` — eight `case` labels with byte-identical
  bodies differing only in the comment.
- `framebuffer/screen_modes.c:905, 989` — `default_clear_screen` and the blanking
  tail of `default_scroll_screen` are the same seven lines, and both fill row-wise
  through the `set_pixel` function pointer while `fill_hline` — added, per its
  comment, as "the fast path for solid PM_NORMAL fills" — sits unused beside them.
  A CLS in MODE 65 is 1.3M indirect calls in IRQ context where it could be 1024
  `memset`s.
- `framebuffer/primitives.c:1092-1106` — the flood queue wraps silently, so PLOT
  133 completes as a partial fill with no notice outside `DEBUG_VDU`. The write
  pointer test is already there; detecting the wrap and abandoning would at least
  make it deterministic.
- `uef_service.c:360-363` — `FINALIZE` on a non-UEF upload leaks the whole tape
  (34 KB stream + up to 1 MB buffer) and wedges it: `uploading` stays true, every
  later op returns `ERR_PARAM`. The sibling one-shot path calls `tape_free()`
  before its identical `"INVALID"` reply.
- `uef_stream.c:148-186` — `magic[]` is read uninitialised when the source is
  shorter than 10 bytes (the `&&` short-circuits before it is written). Benign
  today because both container probes have their own length preconditions, but it
  is one relaxed bound from dispatching on stack residue.
- `usb/mtp_fs.c:2297` — `mtp_container_get_string` reads `2*nchars` bytes with no
  bound against `payload_bytes` and does not NUL-terminate, while this file's own
  bounded `fs_mtp_string_to_ascii` sits 1000 lines above.
- `net_service.c:281-295, 1183-1202, 1504-1525` — three copies of "pop one UDP
  record from the ring", two of them omitting the clamp the third documents as
  mandatory. Unreachable today, but it is exactly the invariant E6 breaks.
- `services.h:37-45` — the static asserts check the range table against itself, not
  each service against its range; `aun_emulator`, `wifi_service` and
  `secure_service` each assert the binding, `net_service` and `fat_service` do not,
  despite `net_service.h:95` stating the requirement in prose.
- `net_service.c:1299, 1417-1418` — return values discarded on the untrusted-server
  path where the identical calls 130 lines away are checked; on a TNFS OPEN whose
  reply parses short, `tnfs_fd` keeps its memset 0 and every later READ uses fd 0.
- `AUN/aun.c:1111-1114` — learn mode never evicts, so 32 spoofed in-subnet sources
  fill `aun_map` and every genuine new peer then gets `AUN_TX_NO_ROUTE`. Opt-in.
- Seven FIQ callbacks call the masking `Pi1MHz_MemoryWrite()` where
  `Pi1MHz_MemoryWrite_FIQ()` is the documented variant for exactly that context
  (`ram_emulator.c:73,82,91`, `helpers.c:131,138,148`, `mouseredirect.c:401`,
  `BeebSid.c:26` — the last being one per SID register write). Their immediate
  neighbours in the same files use `_FIQ` correctly. Not a correctness bug; the
  one place the idiom is applied inconsistently within a single file.
- `Pi1MHz.c:625, 950, 1000` — three comments promise boot-stage forensics from
  `RPI_BootDetail`, which `rpi/rpi.h:56` compiles to `((void)0)` outside DEBUG. Right
  for the per-callback stamp in the hot loop, but the two *boot-time* markers those
  comments describe do not exist in the release image the crash record is read
  from.
- `rpi/mailbox.c:237-253` — `RPI_PropertyAdd`/`RPI_PropertyNewTag` increment
  `pt_index` with no bound against `PROP_BUFFER_SIZE`; `tx_buffer` (the 64 KB UART
  ring) sits immediately after `pt`.
- `rpi/auxuart.c:99-103` — `get_clock_rate(CORE_CLK_ID)` unchecked; now that
  `mailbox.c` legitimately returns 0 on a dead VC, `MU_BAUD` becomes 0x7FFFFFFF and
  the serial port is silently unusable for the rest of the boot.
- `rpi/screen.c:398-407` — `plane_write_fields()` casts unconditionally to
  `rgb_8bit_t*`; `palette` is at 0x20, which in `YUV_plane_t` is the read-only

  `(ctrl & 0xF) == 0xD` — the discrimination belongs next to the cast.
- `rpi/screen.c:42-44, 1279-1281` vs `:1284, 1643` — two comments say banks 4/5 are
  "never selected" and their 2 KB is "spare", but `screen_set_palette` case 5

- `uef_service.c:483-485` — a command 93 that does not start `"IUEF"` falls through

- `fonts.c:271-301` — `default_read_char` reuses its own `y` parameter as a loop
  counter, and `screendata` is sized by `MAX_FONT_HEIGHT` (32) while the buffer it
  is compared against is sized by `MAX_HEIGHT` (14) — two constants for one

- `framebuffer.c:1404, 1240` vs `:1971` — `vdu_enqueue()` reserves *space* for a
  half-received Beeb command but not *position*, so driver-generated text

  byte and its parameters.

## Recommended order

1. **A1** (`arm-start.S` r3) — one instruction, and it is on the kernel7 chain-boot
   path with a Zero 2 W already awaiting a card restore.
1b. **B1a** (the `dead` latch in `vcsm.c`/`auds.c`) — a few lines each, and it
   finishes a fix that is already recorded as done.
2. **D1** (polyphase uncached bit) — six characters, and it makes the whole
   sharper-kernel line of work meaningful.
3. **B3** (`page < 255u`) and **A3**/`screen_allocate_buffer` NULL check — each a
   line or two, each preventing silent corruption.
4. **D2** (YUV horizontal clamp) — it is why the video plane vanishes on every 4:3
   display.
5. **B1** (COPY unlink on abort), **C3** (`fat_open_valid` as an actual gate),
   **A2** (`0x11C06` → `0x11C02`).
6. **F1** needs a decision, not a patch.

Everything in G and H is cleanup with no behavioural risk and can go in any order.
