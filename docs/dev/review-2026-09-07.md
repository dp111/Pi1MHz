# Whole-tree review, 2026-09-07
## C. Beeb-visible hangs and poll-loop stalls

### C4. `fat_service.c` — unbounded FatFs/SD work in FIQ **[noted, not changed]**

`fat_service_command` runs from a `WRITE_FRED` callback and calls
`disk_read`/`f_read` inline; the per-command caps bound the *region*
(`sectors` up to the whole 32 MB disc RAM), not the transfer, so one command
can hold FIQ for ~2 s at the card's bulk rate.

**Disposition (2026-09-07): noted.** The service has always run the Beeb's
own synchronous requests in FIQ - that is its design, stated in its header
comment, and the Beeb-side filing system is blocked waiting on the very
transfer it asked for, so a long command is a long *request*, not a hang.
The Pi side is what pays: no other bus cycle and no poll-loop work during the
transfer.  Bounding a single command would only push a bulk load into several
commands with the same aggregate cost.  The genuine fix is the
latch-and-defer shape the SCSI juke, AUN and net services use (FIQ latches,
the main loop services), which is the CLAUDE.md rule for SD work - a
restructure of the service's command model, and the owner's call.  Left open
for that decision.

## F. Layering

### F1. `BeebSCSI/scsi.c:1156, 745, 1509` — VFS writes are refused with CHECK CONDITION and skip their data-out phase

The code is deliberate and carries its rationale:

```c
/* VFS write-protect: LUN >= 8 is read-only LaserDisc media and the VFS
   ROM never issues WRITE6 ... Refuse at command phase - a tripwire for
   any unexpected writer. */
```

but it contradicts the rule in CLAUDE.md — *"Beeb writes are silently
accepted-and-discarded — never refused with an error, because the Beeb's FS
handshake loops have no timeouts"* — and the filesystem layer contradicts itself
on the same point: `filesystem.c:943-947` states the rule, `filesystemWriteNextSector`
obeys it, while `filesystemWriteAttributes:1203`, `filesystemFormatLun:1240` and
`filesystemOpenLunForWrite:1644` all return false for LUN ≥ 8.

Because the refusal is placed *before* `ITPHASE_DATAOUT`, a writer that does reach
it is left waiting on REQ mid-transfer rather than getting a clean error.

**This is a decision, not a defect — it needs the owner's call**: keep the
tripwire (and accept the rule's exception, ideally written down), or run the data
phase, discard the bytes and return GOOD.

### G7. Three hand-rolled dotted-quad IPv4 parsers **[noted, not changed]**

`teletext_emulator.c` (`ttx_parse_endpoint`), `AUN/aun_config.c` (`parse_ip`),

**Disposition (2026-09-07): noted.** The three have different contracts, not

shared strict parser would be a fourth function serving three call sites.
Not worth the churn.

- `services.h:37-45` — the static asserts check the range table against itself, not
  each service against its range; `aun_emulator`, `wifi_service` and
  `secure_service` each assert the binding, `net_service` and `fat_service` do not,
  despite `net_service.h:95` stating the requirement in prose.
- `net_service.c:1299, 1417-1418` — return values discarded on the untrusted-server
  path where the identical calls 130 lines away are checked; on a TNFS OPEN whose
  reply parses short, `tnfs_fd` keeps its memset 0 and every later READ uses fd 0.
- `AUN/aun.c:1111-1114` — learn mode never evicts, so 32 spoofed in-subnet sources
  fill `aun_map` and every genuine new peer then gets `AUN_TX_NO_ROUTE`. Opt-in.
- Seven FIQ callbacks call the masking `Pi1MHz_MemoryWrite()` where
  `Pi1MHz_MemoryWrite_FIQ()` is the documented variant for exactly that context
  (`ram_emulator.c:73,82,91`, `helpers.c:131,138,148`, `mouseredirect.c:401`,
  `BeebSid.c:26` — the last being one per SID register write). Their immediate
  neighbours in the same files use `_FIQ` correctly. Not a correctness bug; the
  one place the idiom is applied inconsistently within a single file.
- `Pi1MHz.c:625, 950, 1000` — three comments promise boot-stage forensics from
  `RPI_BootDetail`, which `rpi/rpi.h:56` compiles to `((void)0)` outside DEBUG. Right
  for the per-callback stamp in the hot loop, but the two *boot-time* markers those
  comments describe do not exist in the release image the crash record is read
  from.
- `rpi/mailbox.c:237-253` — `RPI_PropertyAdd`/`RPI_PropertyNewTag` increment
  `pt_index` with no bound against `PROP_BUFFER_SIZE`; `tx_buffer` (the 64 KB UART
  ring) sits immediately after `pt`.
- `rpi/auxuart.c:99-103` — `get_clock_rate(CORE_CLK_ID)` unchecked; now that
  `mailbox.c` legitimately returns 0 on a dead VC, `MU_BAUD` becomes 0x7FFFFFFF and
  the serial port is silently unusable for the rest of the boot.
- `rpi/screen.c:398-407` — `plane_write_fields()` casts unconditionally to
  `rgb_8bit_t*`; `palette` is at 0x20, which in `YUV_plane_t` is the read-only
  `y_ctx` fetch context. Guarded today only by both callers checking
  `(ctrl & 0xF) == 0xD` — the discrimination belongs next to the cast.
- `rpi/screen.c:42-44, 1279-1281` vs `:1284, 1643` — two comments say banks 4/5 are
  "never selected" and their 2 KB is "spare", but `screen_set_palette` case 5
  selects them and VP4 `*VOTRANSPARENT` depends on them.
- `uef_service.c:483-485` — a command 93 that does not start `"IUEF"` falls through
  to the legacy path, whose first act is `tape_alloc()` → `tape_free()`, silently
  destroying an open incremental tape.
- `fonts.c:271-301` — `default_read_char` reuses its own `y` parameter as a loop
  counter, and `screendata` is sized by `MAX_FONT_HEIGHT` (32) while the buffer it
  is compared against is sized by `MAX_HEIGHT` (14) — two constants for one
  quantity in two files.
- `framebuffer.c:1404, 1240` vs `:1971` — `vdu_enqueue()` reserves *space* for a
  half-received Beeb command but not *position*, so driver-generated text
  (`"Unsupported screen mode!"`, a font name) can be appended between a command
  byte and its parameters.
