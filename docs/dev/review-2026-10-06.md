## 1. Fix first

These are the findings with the worst consequence.  Each one was re-read
before it went into this list.

### P1. `src/Pi1MHz.c:558` - HVS interrupt mask written to a BCM2835 address on every board  **[BUG, CHECKED]**

```c
uint32_t *ico = (uint32_t *)0x20002000;
ico[0x20/4] = 0x00000000;   // disable HVS interrupts going to the VPU
```

On kernel7 the peripherals are at `0x3F000000` (`rpi/base.h:37`), and
`cache.c` maps `0x20002020` as ordinary memory.  So on Pi 2, Pi 3 and
Zero 2 W this line has two effects:

- The HVS interrupt is never masked.
- A word at 512 MB + 0x2020 is zeroed on every `init_emulator`.  On a 1 GB
  Pi 3 that is ARM heap or JIM RAM.  What it hits on a 512 MB Zero 2 W is
  GUESSED.

The pointer is also not `volatile`.

Fix: `(volatile uint32_t *)(PERIPHERAL_BASE + 0x2000)`.  This is a VPU-facing
change, so kernel7 needs a hardware boot test.

### P2. `src/rpi/arm-start.S:243-354` + `rpi/rpi.ld:115` - kernel.now overwrites the outgoing kernel's `.noinit` while it is still running  **[RISK, MEASURED layout]**

`_copyandreboot` copies the incoming image from `0x8000` up, with the MMU
on.  The live `.noinit` begins at `_edata`.  Symbols from the GCC 13.2
`rpi` release build:

| symbol | address | incoming image that reaches it |
|---|---|---|
| `_edata` | `0xC9A7C` | (current image 793 KB) |
| `chain_magic` | `0xCCD8C` | > ~806 KB |
| `PageTable` (live L1) | `0xD8000` | > ~852 KB |
| `arm_stack` | `0x142000` | > ~1.28 MB |

The committed `kernel.img` is already 800,240 bytes.  The kernel grew by
about 40 KB from V1.37 to V1.39.

- **About 6 KB more growth** and every chain-boot loses `chain_magic`.  The
  incoming kernel can no longer tell it was chain-booted (see D-dev-2).
- **About 50 KB more growth** and the copy overwrites the page table it is
  translating through.  The likely result is a hang that needs a power
  cycle.  INFERRED: the exact symptom.

`chainboot_image_ok` caps only at 4 MB.  Fix, either:

- refuse `length > (uintptr_t)&__noinit_start - 0x8000`; or
- place `.noinit` (and `.bss`) at a fixed high offset, so image growth cannot
  reach them.

Update `docs/dev/chainboot-kernel-now.md` in the same change.

### P3. `src/wifi/webserver.c:2261, 4111, 5413` - the kernel.now buffer outlives its request  **[BUG, CHECKED]**

`kn_buf` is freed in `conn_close` (`:1892`) and `ws_err` (`:7197`).  It is
not freed in `conn_reset_for_next_request`, in `upload_fail`, or on the
chunked "Malformed chunk size" 400.  Scenario on a kept-alive connection:

1. A kernel.now upload fails, for example a multi-part form (`:4455`).
2. The next ordinary `PUT /x.ssd` or `POST /files/...` on that connection
   finds `kn_buf != NULL`.  `dav_put_write_bytes` (`:5189`) and
   `upload_write` (`:4138`) collect the body into RAM and answer 422.  If the
   body starts with an ARM branch, the Pi chain-boots into it.

INFERRED: the unauthenticated drain path (`:6859`) also feeds
`dav_put_write_bytes`.  If so, a PUT with bad credentials on that connection
can reach `kn_take`.

Each leak also pins 4 MB.  The root cause is three hand-written teardown
copies that have drifted apart (W10).  Fix: one
`conn_release_resources()`, used by all three.

### P4. `beeb/1mhz-wifi/src/net_wget.asm:208, 241, 332, 374` - every `*WGET` network error crashes the Beeb  **[BUG, CHECKED]**

These four `jsr pi_wget_network_error` / `jsr pi_wget_timeout` calls end in
`jmp call_claimed` (`util.asm:275`).  That routine pulls two bytes as the
saved X and Y, but they are the JSR return address.  Its RTS then returns
into the stack page.

Scenario: `*WGET http://no.such.host/ F`, or any connect/read error, or the
empty-stream timeout.

Fix: `jmp`, not `jsr`, at all four sites.  The 6502 harness (wifirom suite)
can cover the error path cheaply.

### P5. `src/uef_service.c:598` (`window_lay_out` → `window_scatter`) - publishing the guard over a flat window writes past the tape aperture  **[BUG, CHECKED]**

1. A tape is ready with a flat window of up to `UEF_FLAT_WINDOW` (65,024
   bytes).
2. `uef_service_guard_command` arrives and re-lays that window out in
   151-byte runs, one per page, with no page cap.
3. That is about 431 pages, so it writes JIM offsets up to about `0x1B000`:
   Beeb-visible paged RAM outside the 64 KB aperture.
4. It also publishes a length the host cannot read back.

The test only sends the guard before the tape is opened.

Fix: refuse the guard (or carry the excess to the next window) when
`window_length > UEF_GUARD_WINDOW`, and cap the scatter at 254 pages.

### P6. `src/framebuffer/primitives.c:1613-1665` - `malloc`/`free` in IRQ context with no heap lock  **[RISK, CHECKED]**

The VDU drain runs in `IRQHandler_main` (`Pi1MHz.c:520`), and sprite
definition and reset allocate and free there.  The main loop also allocates
(FujiNet, webserver, video player).  The tree has no `__malloc_lock`.

Scenario: a `VDU 23,27,...` arrives during a main-loop `malloc`, and the
newlib heap is corrupted.

Fix: a static sprite arena, or `__malloc_lock`/`__malloc_unlock` that mask
IRQ.  The arena is the smaller change.

### P7. `src/videoplayer.c:67` - GPU buffer handles kept at fixed low address `0x7C20`  **[RISK, CHECKED]**

This breaks the CLAUDE.md rule (low RAM is VPU/Beeb-shared; ARM state goes in
`.noinit`).  `rpi/bootstage.c:16-19` records that stray bus bytes corrupted
`0x7C00`-`0x7C3F`, the very range this sits in.

`videoplayer_init` runs on every BREAK.  When the magic word matches, it
calls `screen_release_buffer()` on the stored handles.  So a corrupted handle
word frees another owner's GPU buffer (for example the framebuffer's) and
leaks the player's.

Fix: `.noinit` plus the magic word, accepting the cross-build loss as
bootstage does.

### P8. `src/BeebSCSI/harddisc_emulator.c:501` - `hd_wait_ack` reports ACK when it stopped for SEL or reset  **[BUG, CHECKED loop / INFERRED callers]**

The loop also exits on `HD_SEL` or `Pi1MHz_is_rst_active()`, then returns
`true`.  `hostadapterReadByte` then returns the stale `HD_DATA` latch.

Callers that save what they read:

- WRITE6 (`scsi.c:1248-1281`): checks the RST level only.  A BREAK that
  begins and ends inside a slow `f_write`, followed by ADFS reselecting,
  fills the remaining sectors with the selection-ID byte and writes them to
  the image.
- MODE SELECT (`:1578-1653`): no check at all.  Junk geometry goes into the
  LUN's `.cfg`.
- BSSELECT (`:2377`): can jukebox to a junk directory.

Fix: return `HD_ACK != CLEAR`, and make the abort sticky so all three
callers can test it before they save anything.

### P9. Tests: the services suite has not linked since 368e244, and CI runs 2 of 14 suites  **[BUG, MEASURED]**

- **T1.** `src/tests/services` fails to link at HEAD:

## 5. Pi 4 readiness (for the planned Pi 4 build)

The tree already carries some `RPI4` code inherited from PiTubeDirect:

- the GIC disable in `arm-start.S:120`;
- the BCM2711 pull registers in `gpio.c:110`;
- the timer predivider in `armtimer.c:24`;
- the IRQ block in `interrupts.h:57`;
- `OPT_MCU_BCM2711` in `tusb_config.h:53`.

None of it is built: there is no `rpi4` preset or toolchain file, and
`rpi/base.h` knows only `0x20000000` and `0x3F000000`.  PiTubeDirect's Pi 4
port is the model.  What this review saw that a Pi 4 build must deal with
(INFERRED unless marked):

- **Peripheral base and image.**  `0xFE000000` in `base.h` and a new
  `rpi4.cmake` (Cortex-A72, `kernel7l.img`, `arm_peri_high` left off).
  Every hard-coded address has to go; P1 is the only one this review found
  in first-party C.
- **Memory map.**  `cache.c` sizes the VC and peripheral sections from the
  mailbox and `PERIPHERAL_BASE`; check the 0xFE/0xFF ranges map correctly,
  and that `0x7E...` bus addresses (`PERIPHERAL_BASE_GPU`) still translate.
- **Interrupts and FIQ.**  The Pi 4 boots with the GIC-400.  The tree
  disables it and uses the legacy ARMC block; check that FIQ routing for the
  bus doorbell still works that way.  GUESSED: PiTubeDirect relies on
  `enable_gic=0` in config.txt for the same reason.
- **The VPU bus engine** (`vidcore/Pi1MHzvc.s`, owner's file).  VideoCore VI
  has a different clock tree and GPIO block.  The GPIO pull and
  function-select layout already differ (see `gpio.c`), and the VPU code
  writes GPFSEL directly.  This is the hardest part, and it can be tested
  only on hardware.
- **Display.**  The HVS on BCM2711 (HVS5) has a different display-list and
  plane format, and `screen.c` writes it directly, so the plane, palette and
  dim-strip code needs a BCM2711 variant.  The mailbox framebuffer path is
  unaffected.
- **Storage.**  The SD card is on EMMC2 on the Pi 4, not SDHOST.
  `sdcard.c` is SDHOST-specific.  The WiFi SDIO (Arasan, CYW43455) is
  closer to the 3B+ path.
- **USB.**  On the Pi 4 the dwc2 OTG controller sits behind the USB-C
  connector (device-capable, so MTP works).  The USB-A ports are xHCI behind
  the VL805 on PCIe, which TinyUSB's dwc2 host cannot drive, so the USB
  mouse would need the USB-C port in host mode.
  `board_usb_behind_hub()` already returns false for type 0x11.
- **Video.**  Hardware H.264 decode through MMAL still exists on the Pi 4;
  VCHIQ is the same.  GUESSED: no change beyond the base address.
- **Before starting:** fix P1, and the kernel7 VFP save in C5 (the A72 is the
  same register model).
